| Commit | Change |

| `9adde502` | **Defect 44 closed in code.** A film's up-front payment / free-film waiver no longer depends on Redis. (a) The film's debit ref is now `${tokenId}:charge` (was `${compositeId}:charge`), so any function can find the payment in `credit_ledger` from the token alone. (b) New `lib/chat/filmWaiverStore.ts`: `consumeFilmWaiver` asks the database waiver table; where the table is not applied it reads the ledger (`netDebitedForRef > 0`) and makes the single spend a `request_idempotency` claim (that table is in Production). (d) `filmComposite` records the waiver in the database next to the Redis markers. (e) Proposal `proposals/20261014a_film_payment_waivers.sql` (table + 4 service-role-only functions; paid waiver needs a real ledger debit; exactly-once consume by one UPDATE; `void` when fully refunded). |
| `072235e7` | RPC names written literally (schema-drift scanner); the three functions listed as `proposed` in `__tests__/schema-drift.snapshot.json`. |

Semantics of the durable answer: `paid`/`free` → waive; `spent`/`void` → only the master stamped by the first stitch may waive
a re-stitch (an unspent Redis marker can no longer waive twice); `none`/`unavailable` → the previous Redis behaviour, i.e. fail
toward billing.

Known limit of the no-migration path: the single-use claim lives 1 h (`request_idempotency` window cap). A paid film's
stitch started > 1 h after the claim-less replay is billed (safe side). The migration removes the limit.
