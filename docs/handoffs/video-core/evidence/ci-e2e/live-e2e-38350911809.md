## Root cause (DEFECT_REGISTER_FINAL.md row 39) — a product defect, in Production too

The order experiment answered first: the trim failed again in last place, so it was the trim, not the first edit after
Stop/Retry. The row answered the rest. The worker refused the job 20 ms after it was queued, before any download or
ffmpeg. It reads the request back from `generation_jobs.params`, a JSONB column. JSONB returns an object's keys
shorter-first, so `{ op, fromSec, toSec }` came back as `{ op, toSec, fromSec }`.
`lib/agent/media/editPlan.ts` `validateEditRequest` then compared the re-resolved edits with the stored ones as JSON
strings in the order written. The quote and the run check the request as the client sends it back, in the order it was
written, so both answered OK; only the worker refused. 2× (`{ op, factor }`) and slow motion keep their order, which
is why they passed. The same check is in Production (30be5a2). Affected are every edit whose keys JSONB reorders:
trim, volume, adjust (light and colour), erase and the layers (text, logo, sticker). Not affected: speed, fade,
thumbnail, mute, aspect, rotate, grade, motion, overlay, a caption. The old unit round-trip used
`JSON.parse(JSON.stringify())`, which keeps the order, so it never showed this.

Fix c130532: the edits and the plan's frame are compared in one key order (`canonicalJson`); a changed value is still
refused. Regression: `editPlan.test` (a request in JSONB's own key order passes for nine edit mixes, a changed value is
refused, red on the old check) and `leaseIsolation.pg.test` on Postgres 16 + PostgREST (trim, volume and adjust
enqueued through the live lease store, read back from the real JSONB column, delivered; on the old check the worker
answers `invalid_request: the stored plan is not valid`, the same words as this run). Result of the rerun: `live-e2e-38353387827.md` (run 8: 21 / 21; the trim delivered 90 frames on both viewports).
